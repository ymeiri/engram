# Correction and deletion propagation gate v1 — 2026-08-08

## Outcome

The current Engram 0.2.3 worktree passes the bounded deletion propagation gate for Engram-owned
state. The legacy reviewed correction path and compatibility `correct` action remain on the full
MCP surface. Candidate source exposes only `propose_correction` through the selected restricted
coding-agent profile; durable inspection and exact digest-bound application stay on the full
profile. The candidate has not been installed or exercised by native Codex or Claude Code, so the
end-to-end flagship correction journey remains partial.

Through the unrestricted MCP implementation, a reviewed correction promotes the exact replacement
item, marks the old item superseded, records both directions of the relationship and reviewer
evidence, and makes only the replacement guidance available through active listing, orientation,
and unified memory search. The obsolete guidance text is absent from those retrieval responses.

Confirmed `forget` permanently removes the exact canonical item from a real temporary RocksDB
store and purges or rewrites its internal projections. After deletion, the canary and deleted ID are
absent from memory listing, commit log, orientation, unified memory search, graph derivation, and a
recompiled generated vault.

The tests do not use, restart, or modify the installed live daemon or `~/.engram/data`.

## Correction proof

The correction regression starts with active user-stated guidance and a conflicting agent-inferred
replacement that is correctly held in `needs_review`. The `supersede` action requires the exact old
and replacement IDs, reviewer, and rationale. It then verifies:

- the replacement is active and carries manual-review evidence;
- the old item is superseded rather than silently overwritten;
- only the replacement appears in the active list;
- orientation returns the replacement text and not the obsolete text;
- unified scoped memory search returns the replacement text and not the obsolete text.

Historical supersession IDs may remain as lineage metadata; obsolete guidance content is not
eligible agent guidance.

This legacy proof calls the full MCP implementation directly. The installed restricted agent
profile allows memory `add`, `procedure_match`, `get`, `list`, `archive`, and `forget`, but rejects
`supersede`. Candidate source also rejects direct `correct` and exposes the proposal-only action
described below; neither proof establishes that installed native Codex or Claude Code can complete
a correction through their real Engram boundary. Procedure correction is deliberately unsupported.
Broader correction behavior across `changes_since` and regenerated graph/vault lifecycle views also
remains untested after restart.

## Deletion proof

The deletion regression requires `confirm_forget=true`, an exact ID, and a reason. It materializes
a real RocksDB store, a linked knowledge commit, a retrieval trace, and a generated Markdown vault
before deletion. The service and MCP tests together verify removal or scrubbing of:

- the canonical memory item;
- supersession and evidence references held by other memory items;
- knowledge-commit changes and messages naming the item;
- retrieval traces that returned the item;
- feedback associated with the item or deleted trace;
- graph nodes and edges derived from the item;
- the selected generated vault item page, index, and regenerated pages;
- post-delete memory list, commit log, orientation, and unified-search responses.

The persistent regression asserts that `data/CURRENT` exists so it cannot silently fall back to the
in-memory backend.

## Boundary of the claim

Engram can delete canonical state and projections it owns. It cannot prove deletion from arbitrary
copies previously pasted into chat transcripts, external systems, backups, or separately exported
vaults. The forget response reports this boundary and can recompile one explicitly selected
generated vault as part of the confirmed operation; owners must delete other copies separately.

The correction claim is narrower than the deletion claim. The legacy proof covers the underlying
full-profile operation and active retrieval filtering; the candidate proof adds a restricted-profile
proposal route and a separate operator-selected full-profile apply route. This selected profile is
not authentication and establishes neither verified human intent nor reviewer authority. Remaining
closure includes installed/native adoption, a safe procedure-correction lifecycle, and broader
persistent projection coverage.

## Candidate bounded correction proposal/operator split — 2026-09-05

The candidate does not expose direct `correct`, legacy `supersede`, proposal inspection, or
`apply_correction` through the selected restricted agent profile. Instead, an agent may call
`memory(action=propose_correction)` with one exact obsolete ID, proposed title/content, source
evidence, writer identity, and a caller-selected local or related project/task/cwd selector.
Restricted `add` requires `origin=agent_observed|agent_inferred`; it rejects user/tool provenance,
caller actor overrides, and caller-supplied manual review. The service re-fetches the obsolete item,
checks its exact stored scope against the selector, derives replacement kind, scope, confidence,
tags, and review schedule server-side, and forces agent provenance plus `origin=agent_inferred` and
`status=needs_review`.

Proposal creation atomically locks the still-active obsolete item and writes a separate typed
`correction_proposal` record plus its inactive replacement. Ordinary store writers cannot mint or
mutate either server marker. The proposal binds the exact pair and correction-relevant semantic
state with a versioned SHA-256 canonical digest;
retrieval-only timestamps are deliberately excluded so merely reading the old item cannot
invalidate a proposal. Proposal creation returns the proposal/replacement/obsolete IDs, digest,
`intent_verified=false`, and `reviewer_authority_conferred=false`. The obsolete item stays active;
active list, lean orientation, and scoped search continue returning the old guidance and exclude
the pending replacement from active context.

The full operator profile exposes durable scoped `get_correction_proposal` and
`list_correction_proposals` inspection, then `memory(action=apply_correction)`. Apply requires the
server-minted proposal ID, exact expected digest, and the same selector. The service re-fetches
the proposal and both records, checks the pair, kind, scope, pending/active statuses, origin,
evidence, server marker, and canonical digest, then atomically activates the replacement,
supersedes the old item, and marks the proposal applied. Application adds no `manual_review`
evidence and returns `authority_boundary=operator_selected`,
`human_identity_authenticated=false`, `intent_verified=false`, and
`reviewer_authority_conferred=false`; the activated replacement is `active_unreviewed`. An exact
applied-pair retry is idempotent, while wrong digest, scope, status, marker, evidence, or pair fails
closed. Operator selection is an administrative boundary, not authenticated human intent.

These scopes are selectors, not identity authentication or an authorization principal. Project
proposals require the exact project. Task proposals require the exact task plus their
stored project when present. Repository proposals require a cwd at or below the stored local root.
Global/user proposals accept an explicitly local empty boundary. Entity, session, and custom
scopes remain unsupported until a trusted selector exists. Explicit global relevance is rejected.
Remote-only repository correction after a moved checkout remains outside this bounded local-path
selector. Entity, session, custom, and executable `procedure` correction proposals are unsupported.
There is not yet a safe verify-while-inactive atomic procedure-correction workflow; the candidate
does not recommend the unsafe two-call add/verify/direct-correct sequence.

Regressions cover wrong-project creation/application, project-only and sibling task rejection,
exact task success, unrelated/matching-descendant repository paths, global empty-boundary success,
unsupported scopes, wrong digest, changed evidence, wrong status, no manual-review promotion,
active-unreviewed trust, exact retry idempotency, locked current-plan rejection before writing, and
deterministic forget behavior for pending proposal pairs. A storage-level injected proposal-write
failure proves the three-record apply transaction rolls back both memory mutations. A real
two-process RocksDB lost-response regression creates a pending proposal, exits without an ID
sidecar, rediscovers and inspects the exact pair in a fresh process, then applies it and confirms
active retrieval. The effective stdio agent contract rejects direct correction/application and
proposal inspection, manufactured provenance, actor override, and caller manual review; it creates
a real proposal and proves the old text remains the active result.

This installation closes adoption and live-contract drift, not native behavior. No controlled
Codex or Claude Code correction trial has run yet, so the flagship correction criterion remains
partial. The legacy direct `correct` action remains on the full administrative surface for
compatibility but is absent from the agent contract. This design deliberately does not claim
authenticated human intent, reviewer authority, or prevention of semantic contradiction through
other permitted writes/deletion. Proposal-pair creation/apply and pair-aware canonical deletion are
transactional. The same deletion transaction also writes a content-free retry receipt containing
only the exact affected IDs. Telemetry, knowledge-commit, and free-form-reference cleanup remains
sequential and idempotent; a later call, including through a fresh service after restart, resumes
from the receipt, and successful cleanup deletes the receipt. Resumed reports set
`cleanup_resumed=true` and `projection_counts_complete=false`, because their projection counts
cover the successful retry and cannot reconstruct work completed before an earlier failure.
Memory-item reference rewrites use exact-state CAS. The supported commit action mints immutable
commit IDs, but a concurrent raw datastore overwrite of an existing commit and a concurrent new
cross-item reference are outside this bounded linearizability claim. External copies also remain
outside Engram's deletion boundary; do not report native correction completion until one
controlled fresh-session pass per supported host proves proposal-only agent behavior, exact
operator apply, and replacement-only retrieval.
