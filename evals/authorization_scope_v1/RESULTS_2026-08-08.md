# Agent authorization and scope matrix v1 — 2026-08-08

## Outcome

The current Engram 0.2.3 worktree passes the coding-agent authorization and retrieval-scope gate.
The `agent` MCP profile exposes exactly six tools and rejects every other tool before forwarding the
request to the daemon. Action-bearing tools are filtered again to a compact allowlist. Review,
promotion, supersession, commit, migration, installation, graph, lint, telemetry-administration,
and full-vault operations are therefore not delegated to an ordinary coding-agent session.

Across the agent-facing retrieval paths, local scope defaults to the narrowest provable context;
related scope requires a project, task, or registered-checkout boundary; and global scope must be
explicit. Global responses report `authorization_scope_enforced=false` so callers cannot confuse
an all-scope administrative read with an authorization-filtered result.

No uncovered agent-profile path was found, so this slice required no additional authorization code.
The profile contract, scoped behavior, and negative cases are enforced by executable tests rather
than documentation alone.

## Retrieval-scope rules

### Local (default)

Local mode returns only global/user guidance and context that can be tied directly to the current
project, exact task, repository, or registered checkout. Layers whose ownership cannot be proved
abstain before service or filesystem access. Limits are applied after scope filtering, so an
unrelated record cannot consume the result window and hide an applicable record.

### Related

Related mode must resolve a canonical project boundary from an explicit project, exact task, or
registered cwd. Exact-task retrieval excludes sibling-task memory and obligations. Repository
links, work records, telemetry, and legacy records belonging to other projects are filtered out;
layers without provable ownership are omitted rather than broadened.

### Global

Global mode is an explicit administrative all-scope request. It permits cross-project retrieval and
reports `authorization_scope_enforced=false`. The coding-agent profile does not expose the broader
administrative tools or their review/migration/install actions, even though a separately selected
`full` profile can do so.

## Boundary of the claim

This is local capability and data-scope isolation, not multi-user authentication. The agent-profile
proxy prevents an ordinary coding-agent session from invoking hidden tools and actions or asserting
`manual_review` evidence, while retrieval code prevents accidental cross-project broadening. It
does not defend against an attacker who already controls the local OS account, can replace the
Engram binary, can read the daemon bearer token, or can deliberately start the `full` profile.

Private loopback transport, bearer authentication, private data-directory permissions, secret
rejection, and reviewed-memory trust are separate gates. In particular, free-form reviewer identity
on the full administrative profile must not be treated as cryptographic human authentication; the
coding-agent profile addresses that risk by withholding review-changing actions.
