immediate reads could not find the returned records. The daemon log shows a persistent RocksDB

paths, enforces checked responses across every repository query site, and makes daemon readiness
conditional on a reversible datastore write transaction. The candidate has not been installed

The first matching daemon-log entry is from 2026-07-28. The error was still repeating every few

controlled restart.

## Root cause

SurrealDB query execution has two error boundaries:

1. Awaiting `db.query(...)` can succeed and return a response.
2. Individual statement failures are retained in that response and are surfaced by
   `Response::check()` (or by consuming the failed statement with `take`).

The affected Engram mutation paths awaited the query and discarded the response without calling
`check()`. A failed UPSERT/CREATE could therefore be acknowledged as successful by the store,
service, and MCP layers.

The health endpoint is a liveness/build-identity response only. It has no datastore readiness
check, so the poisoned daemon continued to report `status: ok` while storage writes were failing.

## Candidate change and isolated verification

The current-worktree candidate calls `Response::check()` at all 236 repository query sites,
including:

- Memory schema initialization, item UPSERT, item deletion, and knowledge-commit UPSERT
- Entity observation CREATE, keyed UPDATE, archive CREATE, and deletion
- The remaining entity, document, session, tool, coordination, knowledge, work, obligation,
  repository-topology, and telemetry query paths

Two in-memory regression tests install an explicit failing SurrealDB field assertion and verify
that the repository returns `StoreError::Database` and leaves no record behind:

```text
cargo test -p engram-store statement_level_database_errors -- --nocapture

running 2 tests
test repos::entity::tests::add_observation_surfaces_statement_level_database_errors ... ok
test repos::memory::tests::save_memory_item_surfaces_statement_level_database_errors ... ok
```

A source-level contract test inventories repository `.query(...)` calls and fails when a query is
awaited without immediately checking its response. Enabling the invariant exposed a previously
hidden non-idempotent knowledge schema definition; the schema now uses `IF NOT EXISTS` and passes
repeated initialization.

Health schema v3 adds a reversible datastore readiness probe. It creates and deletes a unique
canary inside one transaction and returns HTTP 503 with `storage_ready: false` when any statement
fails. The daemon client parses that response as “alive but not writable,” refuses to route MCP
traffic, and does not remove runtime files or attempt to start a competing RocksDB owner.

Persistent stores also reserve the larger of 512 MiB or 2% of the filesystem. Engram checks this
before opening RocksDB, exposes available and required bytes in health, and rechecks readiness every
30 seconds. A daemon that loses disk headroom or transaction writability cancels itself instead of
continuing an unbounded background-error storm. This bounds storage-failure repetition; it is not a
general maximum-size rotation policy for unrelated daemon logs.
